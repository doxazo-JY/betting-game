# 데일리 노트 — 2026.08.07

## 오늘 요약 (공유용)

전날 발견한 실사용 문제들(DB 커넥션 한도, 새로고침 지연 등)을 실제로 테스트하며 발견한 UI/UX 디테일 6가지를 정리하고 고친 날. 사용자가 "일단 바로 수정하진 말고, 문제 파악하고 어떻게 수정할 건지 이야기 좀 해봐"라고 명시적으로 요청해서, 코드 조사부터 먼저 하고 각 항목의 원인과 수정 방향을 정리해 보여준 뒤 동의를 받고서야 구현했다. 항목은: (1) 두 팀 다 배팅을 확정한 뒤 팀 화면엔 "곧 결과가 발표됩니다"가 계속 떠 있는 게 어색하다, (2) 중계 화면의 "게임 진행 중" 문구가 다른 요소들과 안 어울리고 혼자 따로 논다, (3) 중계 화면에 점수 변화(+/-)가 안 보인다, (4) 패배 표시를 "GAME OVER" 대신 "LOSE"로 바꿔서 "WIN"과 대구를 맞추자, (5) 라운드 종료/시작 반영이 중계 화면은 즉시 되는데 1팀·2팀은 심하게 느리다(같은 크롬으로 여러 개 열어놔서 그런 것 같다는 사용자의 직감), (6) 게임 종료 후 기록표에 이벤트(배팅 배수·전체 점수 교환)도 표시해달라. (1)(2)는 같은 원인(두 화면이 "판정 대기" 상태를 서로 다른 문구·스타일로 따로 구현)이라 공용 배지 컴포넌트 하나로 묶어서 해결했고, (5)는 브라우저가 백그라운드 탭/비포커스 창의 타이머를 강하게 스로틀링하는 문제로 진단해서 탭이 다시 보이거나 창에 포커스가 돌아올 때 즉시 새로고침하는 걸로 보강했다. (6)의 초기 구현안에 이모지(⚡🔄)를 다시 넣었다가 "너무 AI티 난다"는 지적을 받고 장식 없이 텍스트로만 표시하도록 바로 줄였다 — 어제 이미 합의했던 "이모지 대신 텍스트/도형" 원칙을 스스로 까먹었던 셈이라 다시 짚어준 케이스.

## 오늘 한 일

### 1. "게임 진행 중" 상태 통일 — `GameInProgressBadge` 공용 컴포넌트

- 두 팀 다 배팅 확정 후 진행자 판정을 기다리는 상태가 화면마다 다르게 구현돼 있었음: `/play`는 "두 팀 다 배팅을 마쳤어요. 곧 결과가 발표됩니다."라는 평문(+ 대기 점 애니메이션 그대로 유지), `/watch`는 카드들 밑에 `게임 진행 중` 한 줄이 스타일 없이 덩그러니 떠 있었음
- 원인 조사 후 사용자에게 먼저 설명·동의를 구하고, `src/components/GameInProgressBadge.tsx`(테두리 박스 + 대기 점 + "게임 진행 중") 하나를 만들어 두 화면에서 재사용. `/play`에서는 "상대 팀 배팅 기다리는 중"(아직 상대가 확정 전)과 "둘 다 확정, 판정 대기 중"(이 배지)을 조건 분기로 명확히 분리

### 2. 중계 화면 결과에 +/- 포인트 델타 표시

- `/watch`가 결과 발표 시 WIN!/GAME OVER 뱃지랑 원래 배팅액만 보여주고 실제 획득/차감 포인트는 어디에도 없었음(배수 이벤트 있으면 배팅액이랑 실제 델타가 달라지니 더 문제) — `/play` 팀 화면에는 이미 있던 델타 계산·표시를 `/watch`에도 동일하게 추가

### 3. GAME OVER → LOSE!

- "WIN이랑 반대 느낌을 주려면 LOSE로 가자"는 요청. 코드 조사해보니 "GAME OVER"가 세 군데서 쓰이고 있었는데 의미가 서로 다름 — 라운드별 패배 뱃지(`/watch`, `/play`, 2곳) vs 게임 전체 종료 배너(`FinalRanking.tsx`, 1곳). 전자 2곳만 "LOSE!"로 바꾸고 후자는 의미가 달라(진짜 "게임이 끝났다") 그대로 둠 — 이 구분을 먼저 짚어드리고 확인받은 뒤 수정

### 4. 폴링 지연 — 브라우저 백그라운드 탭/창 스로틀링으로 진단

- "라운드 종료·시작이 중계 화면은 바로 반영되는데 1팀·2팀은 1~2분씩 지연된다, 같은 크롬으로 열어놔서 그런가"라는 질문에서 시작. 처음엔 "탭이 여러 개 열려있으면 폴링이 밀린다"고 단순하게 설명했는데, 사용자가 "2팀은 완전히 다른 크롬 계정이었는데 그것도 느렸다"고 반박 — 순수 페이지 가시성(Page Visibility) 이론만으론 설명 안 됨을 인정
- 최종 진단: 크롬은 `document.hidden`(탭이 실제로 화면에 보이는지) 기준 스로틀링과는 별개로, **창이 화면엔 보여도 OS 포커스가 없으면** 추가로 타이머를 늦추는 동작이 있고, 별도 크롬 프로필은 리소스 스케줄링이 더 독립적으로 나뉠 수 있음 — 둘 다 완전히 검증하긴 어려워 "그럴 가능성이 있다" 수준으로 설명하고 넘어감
- 수정: `PollRefresh`에 기존 `setInterval` 외에 `visibilitychange`, `window.focus` 리스너를 추가해서 탭이 다시 보이거나 창에 포커스가 돌아오는 즉시 한 번 더 새로고침하도록 보강(`src/components/PollRefresh.tsx`)

### 5. 게임 종료 후 기록표에 이벤트 표시 — 이모지 넣었다가 바로 뺌

- 조사 결과 두 이벤트(`SWAP_ALL`, `BET_MULTIPLIER`) 모두 실행 시점에 `EventLog.roundId`가 항상 채워져 있었음(둘 다 라운드가 WAITING 상태일 때만 실행 가능하므로) — 배팅 배수는 `Round.multiplier` 필드 자체가 이미 그 정보라 별도 조회 없이 판단 가능하고, 전체 점수 교환은 `EventLog`를 `SWAP_ALL` + `roundId`로 조회해서 판단
- 1차안은 배팅 배수를 "⚡ ×2" 뱃지로, 전체 점수 교환을 "🔄 전체 점수 교환" 장식 구분행으로 제안했는데, 사용자가 "너무 AI티난다 좀 줄여"라고 바로 지적 — 전날 이미 합의했던 "이모지 대신 텍스트/도형" 원칙을 스스로 다시 어긴 것. 장식 없이: 배팅 배수는 라운드 표기 옆에 흐린 텍스트로 `R4 (×2)`, 전체 점수 교환은 해당 라운드 앞에 흐린 텍스트 한 줄("전체 점수 교환")만 추가하는 걸로 축소
- `src/lib/roundHistory.ts`(`RoundHistoryEntry`에 `multiplier`/`swapAllBefore` 필드 추가), `src/components/RoundHistoryTable.tsx`(`.flatMap()`으로 이벤트 구분행 삽입) 수정

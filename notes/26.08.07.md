# 데일리 노트 — 2026.08.07

## 오늘 요약 (공유용)

아침엔 성능 버그로 시작했다 — "진행자 화면에서 1팀 배팅은 바로 뜨는데 2팀은 계속 대기중으로 보인다"는 신고를 받고 코드를 훑어보니, `admin`/`play` 페이지가 폴링(1.5~2초 간격 새로고침)마다 서로 무관한 DB 조회를 순차 `await`로 처리하고 있었다(`play`는 최대 7회 왕복) — 반면 체감상 훨씬 빠르던 `watch` 화면은 4회뿐이었다. `Promise.all`로 병렬화하고, 진행자 화면의 결과 입력 폼에 넘기던 최종 배팅액도 이미 조회해둔 값을 재사용하도록 고쳐 불필요한 쿼리 2개를 없앴다. 여기에 라운드 기록표에 각 라운드·이벤트의 포인트 전/후 값을 원장(`ScoreTransaction`)에서 그대로 읽어와 표시하는 기능과, 게임 종료 후에도 진행자 화면에 남아있던 "게임 종료" 버튼을 숨기는 수정을 묶어 커밋·푸시했다(`0662a45`).

오후부터는 홈 화면 브랜딩/디자인으로 넘어갔다. 먼저 "배팅 게임"이라는 이름이 실제 행사 브랜딩("인투 오락실", "인투"는 청년부 이름)과 안 맞아 보인다는 지적으로 도메인 이름 변경을 검토했는데, Vercel의 무료 `*.vercel.app` 서브도메인이 "프로젝트 생성 시점에만" 자동 발급되고 이름만 바꾼다고 재발급되지 않는다는 걸 확인해 새 프로젝트로 재배포하는 방향으로 정리했다(실행은 사용자 몫 — Vercel 계정 설정이라 대신 안 함). 이어서 타이틀 폰트로 한글 지원되는 도트 폰트(갈무리, Galmuri, SIL OFL 오픈소스)를 찾아 npm으로 필요한 파일만 추출해 웹폰트로 붙였는데, 곧바로 사용자가 PPT 원본 타이틀을 실제 이미지 파일로 직접 전달하면서 이 작업 전체가 폐기됐다 — 웹폰트/SVG 곡선 텍스트 코드를 걷어내고 이미지 자산으로 완전히 대체했다. 받은 이미지가 배경이 불투명해서 앱 배경과 어긋나 보이는 문제는 Python/PIL로 색 거리 기반 알파 매팅을 직접 짜서 해결했다.

이후가 이번 세션에서 가장 오래 끈 부분이다: 사용자가 GPT로 만든 픽셀 장식 CSS 스니펫(`pixel-decoration-code.html` — 하트/별/반짝임/땅/풀숲/나무)을 주며 하트만 빼고 홈 화면에 이식해달라고 했는데, 렌더링을 직접 눈으로 확인할 방법이 없는 상태(아래 참고)에서 CSS 좌표를 손으로 계산해 보내는 방식이 계속 미묘하게 어긋났다. 검은 테두리와 잔디 지그재그가 겹쳐 검은 쐐기 무늬가 생기는 버그, 흙 구멍 무늬가 아예 안 보이는 버그, 화면 넓이에 안 맞게 장식이 가운데로 몰리는 버그, 작게 줄인 나무일수록 공중에 뜨는 버그(`transform-origin` 기본값이 중심이라 축소 시 밑동이 들림 — 이건 진짜 원인 있는 버그였다)를 하나씩 사용자 스크린샷으로 확인받으며 고쳤다. 나무 캐노피 모양은 특히 많이 헤맸다 — 사각 블록 3개 → 톤만 다르게 칠하기 → 계단형 픽셀 원 + 그라디언트 → 울퉁불퉁 비대칭 실루엣 → 겹친 납작 타원 클러스터("최악"이라는 혹평을 받고 롤백)까지 다섯 번 넘게 방향을 바꿨다. 결국 사용자가 실제 나무 그림을 SVG로 픽셀 단위 트레이스한 파일(`<rect>` 2만 2천여 개)을 주면서 "그대로 붙여넣어봐"라고 했고, 이걸 CSS로 재현하는 대신 Python으로 파싱해 PNG로 래스터라이즈하고 하늘·구름·잔디 배경을 제거해 진짜 이미지 자산으로 만드는 쪽으로 전환하면서 일단락됐다. 타이틀 이미지 때와 마찬가지로, 손으로 그리는 CSS 도형보다 실제 이미지 자산이 훨씬 빠르고 확실하다는 게 오늘의 결론.

- 원인: `src/app/play/[teamNo]/page.tsx`, `src/app/admin/[code]/[token]/page.tsx`가 폴링마다 서로 독립적인 Prisma 조회를 순차 `await`로 실행 — `play`는 라운드→내 배팅→상대 배팅→내 결과→상대 결과→이벤트→배수이벤트까지 최대 7회 DB 왕복, `admin`도 비슷하게 여러 번. 반면 `watch`는 4회뿐이라 유독 빨라 보였음

### 7. 홈 화면 배경 장식 — 여러 차례 시행착오 끝에 이미지 자산으로 정착

`pixel-decoration-code.html`(사용자가 GPT로 만든 CSS 장식 스니펫: 하트·별·반짝임·땅·풀숲·나무)을 참고해 하트만 빼고 이식하는 작업. 렌더링을 직접 확인할 방법이 마땅치 않은 채(아래 8번 참고) CSS 좌표를 손으로 계산해 보내는 방식이라 반복적으로 미묘하게 어긋났고, 매번 사용자 스크린샷으로 확인받아 수정하는 왕복이 여러 차례 있었다.

- **배치 버그**: 장식을 `position: absolute`로 좁은 `max-w-md` 본문 안에 넣어서, 데스크톱처럼 넓은 화면에서는 나무가 화면 가운데로 몰려 보이는 문제 → `position: fixed`로 바꿔 뷰포트 전체 기준으로 좌표 계산되게 수정
- **검은 쐐기 무늬 버그**: 잔디 지그재그 실루엣(`::before`)이 땅 박스의 검은 테두리(`border-top`) 영역과 1px 겹쳐서, 지그재그 틈 사이로 하늘색 대신 테두리 검은색이 비쳐 보이는 버그 — 정확한 픽셀 계산으로 겹침을 없애서 해결
- 사용자가 "GPT 코드를 그대로 가져와서 뭐가 문제인지 직접 보자"고 요청 → `pixel-decoration-code.html`의 `.pdp-ground`(74px)를 홈 화면 전용 `.home-ground`로 최대한 그대로 포팅. 기존 전역 `.world-ground`(30px, 모든 화면 공통)는 손댔던 부분을 원상 복구해서 다른 화면에 영향 없게 스코프를 분리
- **흙 구멍 텍스처가 안 보이는 버그**: `radial-gradient` 타일링 방식으로 여러 번 시도했지만 실제로 렌더링되지 않는 원인을 못 찾아, `.world-stars`가 이미 쓰고 있던 검증된 기법(`box-shadow` 다중 사각형)으로 전환해 해결. 이후 "색이 너무 원색이라 뜬금없다"는 피드백으로 색 자체를 기본 흙색에 가깝게 섞고 `filter: blur`로 부드럽게 처리
- **크기 확대**: "배경이 전체적으로 작다"는 피드백으로 땅 74→112px, 나무 90→108px, 별 18→27px 등 1.2~1.5배 일괄 확대
- **나무가 공중에 뜨는 버그(진짜 원인 발견)**: 작게 줄인 나무(`transform: scale(0.75)`)의 밑동이 항상 위로 들려 보이는 문제 — `transform-origin` 기본값이 요소 중심이라, 축소하면 바닥도 같이 위로 딸려 올라가는 게 원인이었음. `transform-origin: 50% 100%`(바닥 중앙)로 고정해서 해결
- **구름/별 모양 왔다갔다**: 흰색 반짝임이 뭉툭한 십자 모양이라 "구름 아니었냐"는 농담을 듣고 진짜 뭉게구름 모양으로 다시 그렸는데, 사용자가 "오히려 애매한 십자 모양이 더 자연스러웠다"며 되돌려달라고 함 → 원래 비율로 복원하되 크기만 키움 → 커진 채로 보니 "뿔 하나만 튀어나온 이상한 모양(변기 같다)"이라는 재지적을 받아, 밑변이 넓고 봉우리가 2개인 제대로 된 구름 실루엣으로 다시 설계. 오른쪽에도 구름 하나 추가
- **나무 캐노피 모양 — 다섯 번 넘게 방향 전환**:
  1. 사각 블록 3개를 겹쳐 그림 → "네모 3개가 합쳐진 것 같다"
  2. 블록마다 톤을 다르게(진초록/기본/연초록) → "따로 노는 것 같다" — 원인은 블록마다 그림자 색·방향이 달랐던 것, 통일해도 재차 "따로 논다"는 지적
  3. 13×11칸 계단형 픽셀 원(clip-path) + `radial-gradient` 단일 셰이프로 전면 재설계 → "완전 원형이라 솜사탕 같다"
  4. 위는 좁고 아래로 갈수록 불규칙하게 넓어지는 비대칭 실루엣으로 재작업 → "낫 배드"지만 패임이 매 칸마다라 너무 잦음
  5. 패임을 3번으로 줄이고 그 사이는 여러 칸에 걸쳐 서서히 넓어지는 리듬으로 재조정 → "괜찮은데 완벽하진 않다"는 평가와 함께, 원본 PPT 참고 이미지 속 두 가지 실제 스타일(겹친 납작 타원 블롭 vs 음영으로 표현한 입체감)을 설명받음
  6. 타입1(크기 다른 납작 8각형 블롭 5개를 겹치는 방식)을 구현했지만 "최악"이라는 혹평 → 5번 버전으로 롤백
- **최종 해결 — 이미지 자산으로 전환**: 사용자가 실제 나무 그림을 SVG로 픽셀 단위 트레이스한 파일(`pixel_tree_original_trace.html`, `<rect>` 2만 2천여 개)을 제공하며 "그대로 붙여넣어봐"라고 요청. CSS로 재현하는 대신 Python으로 `<rect>`를 파싱해 323×323 PNG로 래스터라이즈하고, 색상 휴리스틱(파란 계열 = 하늘, 흰 계열 = 구름)으로 배경을 투명 처리, 하단 잔디 스트립도 잘라내 순수 나무 두 그루만 남긴 이미지(`public/tree-trace.png`)를 만듦. `next/image`로 좌우 배치(오른쪽은 좌우 반전), 기존 CSS 도형 나무 코드(`.home-tree`, `.trunk`, `.canopy`, `--grass-lt` 등)는 전부 제거. 이후 사용자 요청으로 크기 추가 확대(230px/185px)

### 8. 렌더링 확인 도구의 한계

- 사용자 PC의 `localhost:3000`(직접 켜둔 개발 서버)에 브라우저 도구로 접속을 시도했으나, 이 도구가 별도 격리된 환경이라 사용자 로컬호스트에 닿지 않음을 확인
- 별도로 정적 HTML 테스트 파일을 만들어 브라우저 도구로 직접 렌더링해보려 했으나 "Browser 패널이 표시되지 않아 화면을 캡처할 수 없다"는 에러로 이마저도 불가능함을 확인
- 결국 이번 세션의 장식 작업 전체가 CSS 좌표를 손으로 계산해서 보내고, 사용자가 매번 스크린샷을 찍어 확인해주는 방식으로 진행됨 — 검은 쐐기 무늬, 흙 구멍 안 보임 등 반복적인 시행착오의 근본 원인. 이 경험 때문에 타이틀/나무 모두 최종적으로는 CSS 도형 대신 실제 이미지 자산으로 정착함(6, 7번 참고)
